# ASIC Reverse-Engineering Puzzle — GDS In, Answer Out

A fully self-made pipeline that reverse-engineers Jane Street's 2026 ASIC
puzzle straight from the raw `puzzle.gds` layout file — geometric
extraction, gate-level netlist recovery, a from-scratch cell-behavior
library, a self-built gate-level simulator, and a symbolic (SAT/SMT)
search for the answer. No EDA vendor tools (Magic, Netgen, KLayout LVS)
and no Sky130 vendor behavioral models are used anywhere in the shipped
pipeline — every stage is self-implemented from public documentation and
the layout itself.

> Puzzle: [Can you reverse engineer an ASIC?](https://blog.janestreet.com/can-you-reverse-engineer-an-asic/) — Jane Street, 2026

## Setup

Requires Python 3 and a C compiler (for `gdspy`'s native extension).

```bash
git clone <this-repo>
cd asic-puzzle-2026-master

# Create and activate a virtual environment
python3 -m venv puzzle_env
source puzzle_env/bin/activate

# On a fresh Debian/Ubuntu system you may also need:
#   sudo apt install python3-venv build-essential python3-dev

pip install gdspy shapely z3-solver
```

## Running the Pipeline

```bash
cd pipeline_main

# Full pipeline (skips the slow, known-unsuccessful brute-force stage by default)
python3 run_pipeline.py

# Full narrative reproduction, including the brute-force dead end
python3 run_pipeline.py --include-bruteforce

# Resume from a specific stage (e.g. after editing Stage 9)
python3 run_pipeline.py --from stage9_final_netlist.py

# Run just one stage
python3 run_pipeline.py --only stage16_symbolic_search.py
```

Individual stages can also be run directly (`python3 stage1_extract_instances.py`,
etc.) -- each is a standalone script with its own `if __name__ == "__main__"`
entry point and computes its own file paths, so this works regardless of
where it's invoked from.

## Pipeline Overview

### Phase 1-2: Geometric Extraction -> Netlist Assembly (Stages 1-9)

Extracts every standard-cell and clock-buffer instance directly from the
GDS (`gdspy`), resolves each cell's pin positions from its own embedded
labels, extracts all metal/li1/nwell routing geometry and contact/via
positions, and groups touching/via-connected copper into electrical nets
using `shapely` -- with same-layer metal merged chip-wide but `li1` (local
interconnect) scoped strictly per-instance-footprint, per SkyWater's own
design-rule documentation on cell abutment. Top-level ports (`clk`,
`rst_n`, `enable`, `I`, `success`, `O[0:7]`) are resolved from literal
text labels embedded in the GDS itself, cross-referenced against the
puzzle's hint image.

### Phase 3: Cell-Behavior Library (Stage 10)

Every Sky130 cell type used in the design (67 total) is given a boolean
definition derived directly from Sky130's own AOI/OAI naming convention --
not copied from any vendor behavioral model. Built from three generic
constructors (AND-OR-invert, OR-AND-invert, plain N-input) rather than 67
hand-duplicated functions, to minimize the risk of a polarity error across
near-identical variants.

### Phase 4-6: Simulation and Validation (Stages 11-13)

A from-scratch, two-phase gate-level simulator: settle all combinational
logic to a fixed point each cycle, then update flip-flops synchronously.
Validated first against a small synthetic circuit, then -- critically --
against the puzzle's real `example_inputs.vcd` capture from actual
silicon: **100% bit match** on `success` and all 8 output bits across the
full 312-cycle real trace.

### Phase 7: Finding the Answer (Stages 14-17)

Structural analysis initially found a 12-bit shift register fed by `I`,
but an exhaustive 4,096-value brute-force search found nothing (Stage 15,
kept in the repo as part of the honest record). Further structural
analysis revealed `I` actually reaches 58 stateful, input-dependent
flip-flops -- a true search space of roughly 2^121, computationally
unbruteforceable. Stage 16 instead builds a symbolic model of the entire
circuit in Z3 and asks the solver directly for a satisfying input: solved
in under a second. The result was independently re-confirmed through the
separately-built concrete simulator, and proven **unique** by re-solving
with the found solution explicitly excluded (`UNSAT`).

## Key Design Decisions

- **No EDA tools, no vendor behavioral models.** Every stage -- geometric
  extraction, connectivity inference, cell logic, simulation, and search --
  is self-implemented. `magic`/`netgen`/`klayout` LVS tooling was
  evaluated as a pure *debugging* cross-check during the `net_0562`
  investigation only, never as part of the shipped pipeline.
- **Symbolic search over brute force.** Once the true search space was
  understood to be ~2^121, bounded model checking (Z3) was used instead
  of any form of enumeration.
- **Every claim is checked, not assumed.** Extraction was independently
  re-derived from scratch after a total data-loss laptop failure and
  matched the original results exactly (see `HANDOVER_RECOVERED.md`); the
  simulator is validated against real captured silicon before being
  trusted for search; the final answer is proven unique, not just found.
